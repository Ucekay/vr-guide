# LLMモジュール（説明生成）プロンプト設計

この文書は `CONTEXT.md` の「LLMモジュール（説明生成）の確定方針」を実装可能な形（具体的なプロンプトと入出力契約）に落とし込んだものです。設計判断の理由は `CONTEXT.md` と `docs/adr/0001-postgres-server-content-store.md` を参照してください。ここでは「何を」「どう書くか」だけを扱います。

## 1. モジュールの入出力契約

```
LLMモジュール: (question, rdb_data, history) -> response
```

### 入力

| 名前 | 型 | 内容 |
|---|---|---|
| `question` | string | 来場者の今回の発話（任意の言語） |
| `rdb_data` | object | `movies`×`chapters` をJOINして取得した1行。`{chapter_title, movie_title_zh, movie_title_orig, year, essay_md}` |
| `history` | array | `{role: "visitor" \| "guide", content: string}` の配列。同じ Poster ID を見ている間だけ保持され、Poster ID が変わったら呼び出し側で空配列にリセットされる |

呼び出し側（サーバー）が `history` を保持・管理する。LLMモジュール自体はステートレス。

### 出力

```json
{
  "answer": "来場者に読み上げる、来場者の質問と同じ言語の短い説明文",
  "grounded": true
}
```

**2026-10-01追記: `quote`（根拠原文の引用）フィールドは削除した。** 当初はログ検証のためにこのフィールドを含めていたが、GB10実機での計測で「`quote`を含めるだけで出力トークンが約27%増え、応答時間が約25%（約3秒）延びる」ことが分かった（詳細は6節）。この装置はメモリ帯域律速で生成速度が約10トークン/秒固定のため、JSON構造の冗長さがそのまま来場者の待ち時間に直結する。「来場者が待つリアルタイム応答」と「精度検証」という2つの異なる目的を同じ1回の同期呼び出しに同居させていたのがコストの原因だったので、分離する：

- **同期（来場者が待つ）**: `{"answer": ..., "grounded": ...}` のみ。`grounded`の自己申告は（ほぼ）ノーコストなので残す。
- **非同期（来場者を待たせない、ログ・QA用）**: 必要になった時点で、別途バックグラウンドのジョブとして「この回答はessay_mdのどこに基づくか引用せよ」という検証専用リクエストをサンプリングして流す（毎回ではなく、例えば一定割合の会話だけ）。このリクエストの遅さは会話体験に影響しない。

- `answer` だけがTTSに渡される。
- `grounded` はログに残し、「essay_mdの範囲内だけで回答できているか」を後から検証する手がかりとして使う（`score.py`でprecision/recallを実測してきたのと同じ考え方）。
- `essay_md`に根拠が無く「分かりません」と答えた場合は `grounded: true`（＝「分からないと正直に言う」こと自体がGrounded Answeringの原則に従っている状態）とする。
- 一般知識で補ってしまった（≒原則に違反した）場合にのみ `grounded: false` にする、とモデルに明示する。
- モデルの出力がJSONとしてパースできなかった場合のフォールバック: 生のテキストをそのまま `answer` に入れ、`grounded: false` としてログに警告付きで記録する（＝パース失敗を握りつぶさず、検証対象として残す）。

## 2. プロンプトの組み立て方

`rdb_data` は、LLMに渡す直前に次のテンプレートでMarkdown文字列に組み立てる（`CONTEXT.md`の「エージェントへの受け渡し形式」）。

```
# {chapter_title}

## {movie_title_zh}（{movie_title_orig}, {year}）

{essay_md}
```

`history` はシステムプロンプトの後ろに、`role` をそのまま会話ターンとして並べて差し込む。

## 3. システムプロンプト

展示内容（`essay_md`）が中国語であることに合わせ、システムプロンプト自体も中国語で書く（指示文と参照素材を同じ言語に揃えることで、モデルが「どこまでが展示内容でどこからが指示か」を混同しにくくする狙い）。回答の翻訳だけを最後のルールで明示的に指示する。

```text
你是VRChat电影史博物馆的AI导览员。访客现在正站在一幅电影海报前,你的任务是根据下面提供的"展板内容",用口语回答访客的问题。

【展板内容】
{rdb_data_markdown}

【规则,必须严格遵守】
1. 只能根据上面的"展板内容"回答。如果访客问的内容在展板内容里找不到依据,就诚实地说你不知道这个细节,不要用你自己的常识编造答案。
2. 如果访客问的是展板内容里没提到的"另一部电影",不要凭记忆回答,而是引导访客:"请您走到那幅海报前,我再为您讲解。"
3. 如果访客聊的是和电影完全无关的话题,礼貌地说明"我是这里的展览导览员",把话题带回当前这幅海报。
4. 你的回答会被朗读出来,所以:
   - 用3到5句口语化的短句,不要分段、不要用markdown格式(不要加粗、不要列表符号、不要标题)。
   - 不要重复访客的问题,直接说答案。
5. 不管访客用什么语言提问,你的回答都必须翻译成和访客提问完全相同的语言。
6. 最后,只输出一个JSON对象,不要有任何JSON以外的文字,格式如下:
{"answer": "<给访客听的回答原文,用访客提问的语言>", "grounded": <true或false>}
```

## 4. 例

### 例1: 展板内容に書かれている内容を日本語で聞かれた場合

`rdb_data`（era1, 火车进站）を前提に、`question = "この映画が初めて上映されたのはいつですか？"`

```json
{
  "answer": "この映画は1895年12月28日、パリの大カフェにある『インド風サロン』で初めて公開されました。",
  "grounded": true
}
```

### 例2: 展板内容にない情報を聞かれた場合

`question = "导演后来还拍了什么作品？"`（展板内容に後年の作品についての記載なし）

```json
{
  "answer": "不好意思,这幅海报的介绍里没有提到导演后续的作品,我暂时没法回答这个问题。",
  "grounded": true
}
```

### 例3: 他の映画について聞かれた場合

`question = "大都会はどんな映画ですか？"`（現在見ているのは火车进站）

```json
{
  "answer": "それはまた別の展示ですね。そちらのポスターの前に移動していただければ、そのお話をしますよ。",
  "grounded": true
}
```

## 5. 未解決・今後の課題（スコープ外として明示）

- 多言語対応（`CONTEXT.md`で先送り済み）に伴う、`essay_md`自体の多言語化は今回のプロンプトでは扱わない（毎回LLMが動的に翻訳する前提）。
- 話題逸脱時の`grounded`フラグの扱いが曖昧：「別の映画への誘導」応答（本文のルール2）では、実測で`grounded: false`になるケースがあった（本来の「essay_mdの範囲内で答えた」という意味では`true`が妥当とも言える）。ログ検証時にこの揺れをどう扱うか、ルール側で明示的に定義し直す必要がある。
- 非同期の事後検証（6節で触れた「サンプリングして`quote`付きで再検証する」仕組み）は、まだ設計・実装していない。今回は同期応答から`quote`を外すところまでが確定事項で、代替の検証手段は今後の課題として残る。

## 6. 実機ベンチマーク結果（2026-10-01、NVIDIA GB10上）

実際に使用予定のモデル `unsloth/Qwen3.8-27B-NVFP4` を、画像認識パイプラインと同じGB10機で動かし、本プロンプト＋会話例で生成速度を実測した（`scripts/bench_llm_prompt.py`）。

### 必須の推論設定

このモデルは **hybrid thinking モデル**で、何も指定しないと長い思考過程（`<think>...</think>`）を出力してから答えを出す。これを明示的にオフにしないと、出力トークン数が3〜7倍に膨らみ、実用に耐えない。vLLMへのリクエストで以下を必ず指定する：

```json
{
  "temperature": 0.7,
  "top_p": 0.80,
  "presence_penalty": 1.5,
  "chat_template_kwargs": {"enable_thinking": false}
}
```

（Unsloth公式ガイドの「Instruct (non-thinking) Mode」推奨設定と対応）

### 実測値（思考モードOFF、3問×3回=9回の平均）

| 指標 | 値 |
|---|---|
| TTFT | 0.41秒 |
| デコード速度 | 9.5トークン/秒 |
| 1回の応答生成時間 | 4〜10秒（回答の長さに依存） |

### 解釈

- **デコード速度（~6〜10トークン/秒）自体は、思考モードのON/OFFや`CUTE_DSL_ARCH=sm_121a`環境変数の有無によらず一定だった。** サーバーログで`FlashInferCutlassNvFp4LinearKernel`（NVFP4 GEMM）・`FLASHINFER`（attention）が選択されていることを確認済みで、カーネル選択の設定ミスではない。GB10はB200のような高帯域HBMではなく統合メモリ（LPDDR5x系）を積んでおり、27B密モデルの1リクエストずつの生成（バッチサイズ1）は**メモリ帯域で頭打ちになっている**と考えられる（Unsloth公式のB200実測133.7 tok/sとの差は、ハードウェアの帯域差によるもので、設定ミスではない）。
- 思考モードを切るだけでも実質的な応答時間は25〜54秒から4〜10秒に短縮できたが、根本的な解決にはならなかった（下記MTPで判明）。
- 本システムは複数来場者が同時にアクセスするサーバー集中型（ADR 0001）であり、GB10はバッチサイズを上げるとスループットの伸びが相対的に良い（NVIDIA開発者フォーラムの実測でも確認済み）。

### MTP（投機的デコーディング）有効化で約2〜3倍高速化

メモリ帯域律速という診断を踏まえ、`--speculative-config '{"method": "mtp", "num_speculative_tokens": 2}'` を追加してサーバーを再起動し、同じプロンプト・同じ質問で再計測した（Unslothの説明によれば、Qwen系はMTP用の予測ヘッドが量子化モデルに最初から組み込まれており追加ダウンロード不要）。

| 設定 | デコード速度 | 平均応答時間（3〜5文の回答） |
|---|---|---|
| MTPなし（思考モードOFF, `quote`なし） | 6.0 tok/s | 8.41秒 |
| **MTPあり**（同条件） | **21.3 tok/s** | **2.66秒** |

MTPは「1回の重み読み込みで複数トークン分の候補を出し、まとめて検証する」仕組みのため、メモリ帯域がボトルネックのこのハードウェアと相性が良く、実測でも約3.5倍のデコード速度向上・約3倍の応答時間短縮が確認できた。**本番運用ではMTPを既定で有効にする。**

起動ログに以下の警告が出るが、動作自体には支障がない（将来vLLM/FlashInferが対応すればさらに速くなる余地がある、という意味の制限事項）:
```
Fused multi-step draft decode is not supported by attention backend(s) FLASHINFER;
falling back to rebuilding attention metadata between draft steps.
```

MTP有効時のサーバー起動コマンド:
```bash
vllm serve unsloth/Qwen3.8-27B-NVFP4 --port 8000 --gpu-memory-utilization 0.6 \
  --speculative-config '{"method": "mtp", "num_speculative_tokens": 2}'
```
