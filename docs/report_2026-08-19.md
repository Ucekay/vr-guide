## 0. 一行で言うと

Windows 上にあった「VRのスクリーンショットから映画ポスターを言い当てるプログラム」を Linux + GB10 に移して動くようにし、**Windowsでの出力と1件も違わずに再現**した上で、精度 F1 0.960 / 1枚あたり 126 ms という数字を実測しました。

そして測った結果、**このパイプラインで次に手を入れるべき場所は、記述子でも照合アルゴリズムでもなく「1つの画面に2枚ポスターが写っているときに2枚目を取りこぼす」ことだ**と結論しました。取りこぼし3件のうち2件がこれで、残り1件は閾値が1足りなかっただけです。**誤答は0件**でした。

この結論は、より新しい手法（DINOv3、EDM など）への差し替えを今は行わない、という判断を含みます。理由は §7 に書きます。

## 1. そもそも何を作ろうとしているのか

### 1.1 最終的に作りたいもの

VRChat 上に「映画史博物館」というワールドがあります。壁に映画ポスターが時代順（era1〜era7）に貼ってあり、ユーザーはその中を歩き回れます。ここに**ガイドエージェント**を置きたい。ユーザーが見ているポスターについて、「これは1895年のリュミエール兄弟の『ラ・シオタ駅への列車の到着』で……」と喋ってくれるAIです。

そのために必要な最初の部品が、**「今ユーザーが見ている画面に、どのポスターが写っているか」を当てること**です。ここができないと、エージェントは何について喋ればいいのか分かりません。今回の実験は、この部品だけを対象にしています。喋る部分（LLM）は今回一切扱っていません。

### 1.2 なぜ画像処理でやるのか

VRの中なら、視線の先にあるオブジェクトを直接プログラムから問い合わせれば済むように思えます（レイキャストと言います）。実際、既存のVR博物館ガイド研究の多くはそうしています。

それでもこれを画像でやる理由は、**他人が作ったワールドでは、その問い合わせが成立しないから**です。VRChat のワールドに置かれたオブジェクトの名前は制作者が自由に付けたもので、`Plane_042` のような無意味な名前が普通です。ワールドの制作者でない限り、「このオブジェクトは『市民ケーン』のポスターである」という情報はどこにも存在しません。存在するのは画面のピクセルだけです。

さらに、録画・スクリーンショット・360度動画といった、そもそもプログラムが介入できない素材も同じ扱いができます。

### 1.3 この問題は「画像認識」ではない ── ここが一番大事

「ポスターを認識する」と聞くと、犬と猫を見分けるような画像分類を思い浮かべるかもしれません。この問題はそれとは根本的に違います。

VR内に表示されているポスターは、**参照データベースに入っている画像そのもの**を3Dの板に貼り付けたものです。同じピクセルデータが、斜めから見られ、小さく写り、部屋の照明で暗くなり、圧縮されているだけです。**新しい画像を「理解」する必要はなく、「同じ画像を探す」だけでいい。**

この違いが決定的なのは、探索の手がかりが「意味」ではなく「幾何」になるからです。ポスターは平面なので、参照画像と画面内のポスターの関係は**ホモグラフィ**という8つの数字だけで完全に記述できます（後述）。「この対応関係は1枚の平面で説明が付くか？」という検算ができる。犬と猫の分類にはこの種の検算は存在しません。

このタイプの問題は、学術的には **instance-level retrieval**（個体レベル検索）や **image copy detection**（複製画像検出）と呼ばれます。一般物体認識とは参照すべき先行研究も評価指標も違います。**この認識を取り違えると、必要のない新しいモデルを持ち込んで、効かない場所に労力を注ぐことになります。**

## 3. 手法の説明：中で何が起きているのか

パイプラインは5段階です。図にすると:

```
スクリーンショット (1920×991)
  │
  ├─① 画面の中から「額縁っぽい四角形」を探す           … 古典的画像処理
  │     → 平均 4.0 個の候補領域
  │
  ├─② 各候補を切り出して 1024px に拡大、明るさを補正   … 古典的画像処理
  │
  ├─③ 各候補から特徴点と記述子を抽出                   … ニューラルネット (SuperPoint)
  │
  ├─④ 327枚 × 5スケール = 1635件の参照に投票させ、
  │     上位候補を絞る                                  … 行列積1回
  │
  └─⑤ 上位候補それぞれについて「1枚の平面で説明できるか」
        を検算し、説明できた対応点の数を信頼度とする    … RANSAC
        → 閾値を超えたものだけ出力。超えなければ「分かりません」
```

以下、各段を説明します。

### 3.1 ① 額縁候補の検出（Canny → 輪郭 → 多角形近似）

なぜこれが必要かというと、**ポスターは画面の中で非常に小さいから**です。今日この39枚で実測しました:

| | 値 |
|---|---|
| 画面内のポスターの長辺 | 最小 **55 px** / 中央値 260 px / 最大 805 px |
| 画面幅(1920px)に占める割合 | 2.9% 〜 41.9% |
| 参照画像の長辺 | 最小 200 px / 中央値 1109 px / 最大 3926 px |
| **参照と画面内の大きさの差** | **中央値 4.3倍、最悪 72倍** |

1920px の画面をそのまま特徴抽出にかけると、55px のポスターからは特徴点がほとんど取れません。だから先に「そこにポスターがありそうな四角形」を見つけて、切り出して拡大する必要があります。

その見つけ方は、深層学習ではなく古典的な画像処理です:

1. **Canny エッジ検出**（Canny 1986）で輪郭線を抽出。閾値を3段階（20/45/90）変えて3回走らせ、明るい部屋でも暗い部屋でも取りこぼさないようにしています。
2. `cv2.findContours` で閉じた輪郭を拾う。
3. **Douglas–Peucker アルゴリズム**（`approxPolyDP`）で輪郭を折れ線に単純化し、**頂点がちょうど4つで凸なもの**だけ残す。額縁は四角いので。
4. 極端に細長いもの（辺の比が8倍超）や小さすぎるもの（辺12px未満）を捨てる。
5. 重なっている候補を面積の大きい順に残す（**NMS**: Non-Maximum Suppression）。

これで足りるのは、**博物館のポスターが「平らな壁に貼られた四角い平面」という、輪郭検出が最も得意とする形をしているから**です。一般の物体検出器を持ち込む必要はありません。

さらに、候補リストの末尾に**必ず画面全体**を追加します。ポスターが画面いっぱいに写っている場合、それを囲む輪郭が画面外にあって検出できないためです。この保険が無いと、一番簡単なはずの至近距離のケースで失敗します。

> **実測されている落とし穴**（前任者の記録）: エッジ検出を960px に縮小して高速化しようとしたところ、3枚のスクショで**候補が0個**になりました。額縁の細い枠線がぼけて消えるためです。節約できるのは10ms で、割に合いません。既定は原寸のままです。

### 3.2 ② 切り出し・拡大・局所コントラスト補正（CLAHE）

見つけた四角形の外接矩形に20%の余白を付けて切り出し、**長辺が1024pxになるまで拡大**します（最大10倍まで）。これで「小さいクエリ vs 大きい参照」が「同じくらいの大きさ同士」の比較になります。

拡大した**後**に **CLAHE**（Contrast Limited Adaptive Histogram Equalization, Zuiderveld 1994）をかけます。これは画像を小さなタイルに分割し、タイルごとに明るさの分布を引き伸ばす処理です。博物館には照明を落とした暗い部屋があり、そこのポスターは真っ暗に潰れています。

**切り出した後にかけるのが重要**です。画面全体に対してかけると、ポスターは全ピクセルの2%程度しか占めないので、その2%の明暗はほぼ無視されます。切り出してポスターが画像の全部になって初めて、その中の明暗が伸びます。

### 3.3 ③ 特徴点抽出（SuperPoint）── 唯一のニューラルネット

**特徴点（keypoint）**とは、画像の中で「他と見間違えにくい目印になる点」です。角、文字の端、模様の交差点などが選ばれます。平坦な壁や単色の空はここに含まれません。

**記述子（descriptor）**とは、その点の周りがどう見えるかを数値ベクトルにしたものです。ここでは **256次元、長さ1に正規化されたベクトル**です。長さ1に揃えてあるので、2つの記述子の**内積がそのままコサイン類似度**になります。この性質が後段の速度に効きます（§3.4）。

使っているのは **SuperPoint**（DeTone et al., CVPRW 2018）です。畳み込みニューラルネットで、1回の順伝播で特徴点の位置と記述子を同時に出します。学習方法が特徴的で、人手のラベルを使いません。合成図形で初期版を作り、それを実画像に大量のホモグラフィ（射影変換）をかけて適用し、「どんな変形をかけても同じ場所に出る点」を正解として自己教師あり学習します（homographic adaptation）。**「視点が変わっても同じ点が出る」ように直接学習されている**わけで、まさに今回の用途に合致します。

実装と学習済み重みは [cvg/LightGlue](https://github.com/cvg/LightGlue) リポジトリのものを使っています。ただし**LightGlue 本体（照合器）は使っていません**。理由は §3.5 に書きます。

1つの切り出し領域につき最大1024点を抽出します。

### 3.4 ④ 候補の絞り込み（記述子バンクへの投票、行列積1回）

327枚の参照画像それぞれについて、**5つの解像度（長辺 1024 / 700 / 480 / 320 / 220 px）で特徴を抽出**して保存してあります。327 × 5 = **1635件**、合計108万点の特徴点です。

なぜ5解像度かというと、**SuperPoint は大きさの違いに弱いから**です。前任者の記録によれば、**1.5倍の大きさの差があるだけで投票結果はほぼノイズになり**、単一解像度のデータベースでは正解が28位に沈んだものが、5解像度にすると1位になりました。SIFT のような古典手法はスケール不変性を設計に組み込んでいますが、SuperPoint は持っていません。**足りない不変性を、モデルではなくデータベース側の総当たりで補っている**構造です。これは記憶容量（560 MB）を計算量の代わりに払う設計判断です。

絞り込みの手順:

1. 全1635件の記述子から、各件につき強い順に256個を取り出して**1枚の巨大な行列**に積む（39万7千行 × 256列）。
2. クエリ側の強い順512点の記述子（512行 × 256列）と、この行列の**転置を1回だけ掛ける**。
3. 各クエリ点について、最も似ている行を探す。コサイン類似度が **0.80** を超えていれば、その行が属する参照画像に1票入れる。
4. 票数の多い順に上位を候補にする。

**なぜ1回の行列積にまとめるのか。** 1635件を1件ずつ比較しても、掛け算の総数は同じです。しかし実測で**1件ずつだと約700ms、まとめると約20ms**でした。35倍の差は、Python から GPU を1635回叩く呼び出しのオーバーヘッドと、GPU が大きな行列で初めて出せる並列度によるものです。**「同じ計算量なら同じ時間」は GPU では成り立たない**という、この手のパイプラインで最も効く実装知識です。

この設計の副産物として、票は「どの参照画像か」だけでなく「どの解像度か」まで同時に選びます。つまり検証段には「この画像を、この大きさで」という形で候補が渡ります。

### 3.5 ⑤ 幾何検証（相互最近傍 + Lowe比率検定 + RANSAC）

投票はあくまで「似た点がたくさんある」という統計です。偶然似ることもあります。ここで**幾何的な検算**を入れます。

**ホモグラフィ**とは、平面を別の視点から見たときの座標変換で、3×3行列（自由度8）で表せます。ポスターは平面なので、参照画像上の点 (x, y) と画面上の対応点 (x', y') の間には、**必ず1つのホモグラフィが全ての対応点に対して同時に成り立ちます**。逆に言えば、1つの行列で説明できない対応は偽物です。

手順:

1. **相互最近傍（mutual nearest neighbour）**: クエリ点 A の最も似た参照点が B で、かつ参照点 B の最も似たクエリ点が A のときだけ、対応候補として残す。片思いは捨てる。
2. **Lowe の比率検定**（Lowe, IJCV 2004、SIFT の論文）: 1位の距離が2位の距離の 0.90 倍より短くなければ捨てる。「2番目の候補と大差ない」対応は曖昧なので使わない、という発想です。
3. **RANSAC**（Fischler & Bolles 1981）実装は **MAGSAC++**（Barath et al., CVPR 2020、OpenCV の `USAC_MAGSAC`）: 対応の中から4組をランダムに選んでホモグラフィを計算し、残りの対応がどれだけそれに従うか数える。これを2000回繰り返し、最も多く支持された変換を採用する。この変換で6px以内に収まった対応を **inlier（内点）** と呼びます。
4. **形の妥当性検査**: 得られたホモグラフィで参照画像の四隅を画面に投影し、その四角形が**凸で、面積が極端でない**ことを確認する。折り畳まれた四角形や、面積が画面の4倍になるような変換は、数式上は解けていても物理的にありえないので捨てます。

**inlier の個数がそのまま信頼度になります。** 「1つの平面変換で同時に説明できた対応点の数」なので、偶然似ただけの記述子はここを生き延びられません。今日の実測での分離具合:

| | inlier 数 |
|---|---|
| 正解のペア（36件） | **10 〜 592**（中央値 244） |
| 間違った参照とのペア（34件） | **最大 5** |

**5 と 10 の間に、1件も無い空白があります。** これは偶然ではなく、上記の検算が効いていることの直接的な証拠です。

#### なぜ LightGlue（照合器）を使わないのか

LightGlue は SuperPoint とセットで使われる学習ベースの照合器で、上記1〜2をニューラルネットで置き換えるものです。前任者はこれを使わない判断をしており、その理由は測定に基づいています:

| | 1ペアあたりのコスト | 39枚での成績 |
|---|---|---|
| LightGlue 照合 | 約 19 ms | 34/39 |
| 相互最近傍 + RANSAC | 約 0.5 ms | **36/39** |

40倍安い。そして**安いから成績が上がっています**。1画面あたりの検証回数の予算（既定32回）が同じなら、1回0.5msの手法は候補を広く試せます。この段階に来る時点でクロップは既に拡大されて大きさが揃っており、候補も数件に絞られている ── つまり**古典的な記述子照合が最も得意な条件が整えられている**ので、学習ベースの照合器が持つ強み（大きな視点変化への頑健性）を使う場面がありません。

**前処理で問題を簡単にしてから、簡単な道具で解く。** このパイプラインの設計思想はこれです。

### 3.6 検証予算の配り方

検証は1画面あたり最大32回まで、と決めています。この32回を**候補ごとに均等に割らず、票数の高い順に全体から使います**。

理由: 画面には平均4.0個の候補領域があり、その多くは壁の模様や影で、ポスターではありません。均等配分だと、そういう空振り領域にも同じ回数を使うことになります。全体プールから票数順に使えば、空振り領域はほぼ0回で済み、その分を「小さく写っていて票は弱いが正解」の候補に回せます。

さらに、ある領域で inlier が80を超えたら**その領域については確定として打ち切ります**。

## 4. 今日やったこと（1）── 環境の移送

### 4.1 移送先の環境

| | |
|---|---|
| CPU アーキテクチャ | aarch64（ARM）※移送元の Windows は x86_64 |
| GPU | NVIDIA GB10、compute capability **12.1 (sm_121)** |
| ドライバ / CUDA | 580.159.03 / **CUDA 13.0** |

**ここが最初の障害でした。** PyPI から普通に `pip install torch` で入る aarch64 版の PyTorch は sm_121 向けのカーネルを含んでおらず、GPU上で実行しようとすると `no kernel image is available` で落ちます。PyTorch が配っている **cu130 専用インデックス** から取る必要があります。

そこで `pyproject.toml` で torch と torchvision だけ取得先を切り替えました:

```toml
[tool.uv.sources]
torch = { index = "pytorch-cu130" }
torchvision = { index = "pytorch-cu130" }

[[tool.uv.index]]
name = "pytorch-cu130"
url = "https://download.pytorch.org/whl/cu130"
explicit = true
```

`explicit = true` は「明示的に指定されたパッケージだけをここから取る」という意味です。これを付けないと、他の全パッケージもこのインデックスを見に行きます。

結果 `torch 2.13.0+cu130` が入り、`get_device_capability()` が `(12, 1)` を返し、行列積が GPU 上で走ることを確認しました。

### 4.2 uv でのプロジェクト化 ── `uv init --package` を選んだ理由

`uv init` には5つの形式があり、生成される構造が違います。どれを選ぶかは「このコードが何であるか」の宣言なので、適当に選ぶと後で構造と実態がずれます。

| 形式 | 生成物 | 今回の判断 |
|---|---|---|
| `uv init`（既定） | `main.py` 1枚。パッケージ化しない | **✗** モジュールが4つあり、互いに `import` し合っている。1枚に収まらない |
| `uv init --lib` | `src/` 配下にライブラリ。ビルド設定付き | **✗** 「ライブラリ」は他人が `import` して使うもの。これは自分で走らせる実験コード |
| **`uv init --package`** | `src/` + `[project.scripts]` + ビルド設定 | **✓** モジュールとして `import` でき、かつコマンドとして実行できる |
| `uv init --script` | PEP 723 形式の単一ファイル | **✗** 規模が違う |
| `uv init --bare` | `pyproject.toml` だけ | **✗** 結局パッケージ設定を手書きすることになる |

このコードの実態は「**互いに import し合う複数モジュールと、3つのコマンドライン入口（DB構築・照合・採点）を持つ、自分で走らせるアプリケーション**」です。それを過不足なく表現するのが `--package` です。

具体的には、こう書けるようになりました:

```toml
[project.scripts]
build-db = "vr_guide.build_db:main"
match    = "vr_guide.match_fast:main"
score    = "vr_guide.score:main"
```

```bash
uv run match --db db/fast.pt --query data/queries --out-csv out/repro.csv
```

## 5. 今日やったこと（2）── 実験と測定

ここからが本題です。移送しただけでは「動くようになった」以上のことは言えません。**移送が正しいことの証明**と、**このパイプラインの実力の測定**を行いました。

### 5.1 実験A: 移送の正しさの検証

移送先で正しく動いていることを、精度が「それらしい値」であることでは判断できません。たまたま似た値になることがあるからです。**Windows で得られていた出力と、検出結果の集合が完全に一致するか**を照合しました。

結果: **39枚すべてについて、検出されたポスターの集合が完全一致**。

（inlier の個数だけは微妙に違います。例: 438100_38 が 350 → 354。RANSAC は乱数を使うので実行ごとに数点ずれます。判定結果に影響する差ではありません。）

**つまり**: アーキテクチャ（x86_64 → aarch64）、OS、CUDA バージョン、OpenCV バージョンが全部変わっていますが、パイプラインの挙動は変わっていません。以降の測定値を、移送元の環境と地続きのものとして扱えます。

### 5.2 実験B: ベースライン測定

```bash
uv run match --db db/fast.pt --query data/queries --out-csv out/repro.csv --bench
uv run score --results out/repro.csv --labels data/labels_era1.csv --lang en
```

| 指標 | 値 | 意味 |
|---|---|---|
| 完全正解 | 36/39 (92.3%) | 過不足なく答えられた画面の数 |
| **precision** | **1.000** | 答えたもののうち正しかった割合。**誤答ゼロ** |
| recall | 0.923 | 答えるべきもののうち答えられた割合 |
| F1 | 0.960 | 上2つの調和平均 |
| 速度 | **126 ms/枚 (7.9 fps)** | |

段階別の内訳（1枚あたり平均）:

| 段階 | 時間 | 全体比 |
|---|---|---|
| ③ 特徴抽出 | **78.5 ms** | 62% |
| ④ 投票検索 | 21.6 ms | 17% |
| ① 額縁検出 | 6.8 ms | 5% |
| 画像読み込み | 6.4 ms | 5% |
| ⑤ 幾何検証 | 6.1 ms | 5% |
| ② GPU転送 | 1.1 ms | 1% |

**この内訳が言っていること**: 時間の6割は特徴抽出です。そして特徴抽出は1画面あたり平均4.0個の候補領域に対して個別に走るので、1領域あたり約19msです。**速度を上げたければ、候補領域の数を減らすか、抽出器を軽くするしかありません。**照合や検証を速くしても、合計126msのうち6msしか削れません。

### 5.3 実験C: 取りこぼし3件の解剖

「92.3%」という数字だけでは、何を直せばいいのか分かりません。3件を個別に見ました。

| 画面 | 正解 | 出力 | 何が起きたか |
|---|---|---|---|
| `438100_50` | `factory_gate_01` と `_02` の2枚 | `_02` のみ（97 inliers） | **2枚写っているうち1枚しか出さなかった** |
| `438100_61` | `train_robbery_02` と `_03` の2枚 | `_03` のみ（85 inliers） | 同上 |
| `438100_51` | `factory_gate_02` | 出力なし | **正解が1位に来ているが inlier が9で、閾値10に1足りない** |

**「で、つまり？」**

1. **正解が候補順位から外れて消えた例は0件です。** 3件とも、正解は正しく見つかっていて、出力の段階で落ちています。**つまり検索段（①〜④）の上限は 39/39 であり、そこは詰まっていません。**
2. **3件のうち2件が「同じ原因」です。** 1画面に複数枚あるときの2枚目の扱い。これが単独で最大の失敗要因です。
3. 残り1件は閾値の話で、手法の問題ではありません。

さらに、**ポスターが写っていない2枚（`438100_54`, `438100_70`）は両方とも正しく「該当なし」と答えました。** 誤検出が0件だったのはこれを含んでいます。

### 5.4 実験D: 閾値の感度を測る

`--min-inliers`（これ以上の inlier があれば答える、という閾値）を10段階振りました。既定は10です。

| min-inliers | 完全正解 | 誤答(FP) | 取りこぼし(Miss) | precision | recall | F1 |
|---|---|---|---|---|---|---|
| 5 | 20/39 | **23** | 2 | 0.617 | 0.949 | 0.747 |
| 6 | 36/39 | 1 | 2 | 0.974 | 0.949 | **0.961** |
| 7 | 36/39 | 1 | 2 | 0.974 | 0.949 | 0.961 |
| 8 | 36/39 | 1 | 2 | 0.974 | 0.949 | 0.961 |
| 9 | 36/39 | 1 | 2 | 0.974 | 0.949 | 0.961 |
| **10（既定）** | 36/39 | **0** | 3 | **1.000** | 0.923 | 0.960 |
| 12 | 35/39 | 0 | 4 | 1.000 | 0.897 | 0.946 |
| 15 | 35/39 | 0 | 4 | 1.000 | 0.897 | 0.946 |
| 20 | 35/39 | 0 | 4 | 1.000 | 0.897 | 0.946 |
| 30 | 34/39 | 0 | 5 | 1.000 | 0.872 | 0.932 |

**この表から言えること:**

1. **5 と 6 の間に崖があります。** 誤答が 1 → 23 に跳ねる。これは §3.5 で見た「間違った参照の inlier は最大5」と正確に対応しています。5以下を許すと、偶然の一致を全部拾ってしまう。
2. **6〜9 は全く同じ挙動です。** 4段階にわたって数字が1つも動かない。**つまりこの閾値は、慎重に調整しないと崩れるような繊細なものではありません。**「たまたま良い値に合わせ込んだ結果」という疑いを、この平坦さが否定します。
3. **6〜9 と 10 の違いは、`438100_51`（正解、inlier 9）を拾うか、誤答1件を出すか、のトレードです。** F1 では 0.961 対 0.960 でほぼ同じ。数字では決まりません。

**私の判断: 既定の10 を維持すべきです。** F1 が同じなら、どちらを選ぶかは用途で決まります。作ろうとしているのは博物館のガイドです。ここでの誤答は、**ユーザーが見ている作品とは別の映画について、AIが自信を持って解説を始める**ことを意味します。取りこぼしは「これについては分かりません」と言うだけです。**回復可能な失敗（沈黙）と、回復不能な失敗（嘘）を、同じ1件として扱ってはいけません。** F1 は両者を対称に扱う指標なので、この判断は F1 では表現できません。

### 5.5 実験E: ニューラルネットは本当に必要か（SIFT との比較）

このパイプラインで学習ベースなのは SuperPoint だけです。ここを **SIFT**（Lowe 2004、1999年発表の古典手法）に差し替えて、同じデータで測りました。他は一切変えていません。

```bash
uv run build-db --ref-dir data/refs --out db/sift.pt --extractor sift --max-kp 1024 --scales 1024 700 480 320 220
uv run match --db db/sift.pt --query data/queries --out-csv out/sift.csv --bench
```

| | 完全正解 | 誤答 | precision | recall | F1 | 速度 | 特徴抽出時間 |
|---|---|---|---|---|---|---|---|
| **SuperPoint** | 36/39 (92.3%) | 0 | 1.000 | 0.923 | 0.960 | **126 ms** | **78.5 ms** |
| **SIFT** | **37/39 (94.9%)** | 0 | 1.000 | **0.949** | **0.974** | 351 ms | 306 ms |

**SIFT の方が1枚多く正解しました。** そして 2.8倍遅い。

この差をどう読むべきか。39枚のデータセットでは、1枚が 2.6 ポイントに相当します。Wilson 法で95%信頼区間を出すと:

- SuperPoint: 92.3% [79.7, 97.3]
- SIFT: 94.9% [83.1, 98.6]

**区間はほぼ完全に重なっています。この39枚では、両者の精度差は測れていません。**（前任者が Windows 上で行った同じ比較では、SIFT は 35/39・誤答1件と、逆の結果が出ています。この食い違いの原因は特定していません。OpenCV のバージョン差が疑わしいですが未検証です。**逆向きの結果が出るということ自体が、この差がデータセットサイズに対して小さすぎることの傍証です。**）

一方、速度差 126ms 対 351ms は測定として明確です。

**私の主張: SuperPoint を使う理由は、精度ではなく速度です。** 「深層学習の方が精度が良いから」という説明は、少なくともこの39枚では支持されません。この区別は実用上重要で、**もし将来この処理を Quest などのスタンドアロン端末（GPUなし、または非力なGPU）に載せるなら、SuperPoint を選ぶ根拠は消えます。**その環境では SIFT の CPU 実装の方が現実的でしょう。逆に、GPUのあるPCで動かし続けるなら、2.8倍の速度差は素直に効きます。

**選択の根拠を「精度」だと誤認したまま環境を移すと、判断を誤ります。** 今回それを潰せたことが、この実験の副産物です。

### 5.6 実験F: スケールギャップの実測

§3.1 の表の数値です。正解ラベルのペアについて実際にホモグラフィを解き、参照ポスターの四隅を画面に投影して、画面内でのポスターの大きさを測りました（38件の検証済み検出）。

- 画面内のポスター長辺: **55 〜 805 px**（中央値 260 px）
- 参照画像長辺: 200 〜 3926 px（中央値 1109 px）
- **大きさの比: 中央値 4.3倍、最悪 72倍**

**これがこのパイプラインの設計全体を説明します。** ②の「1024pxまで拡大」も、④の「5解像度のデータベース」も、この 4.3倍〜72倍のギャップを埋めるための措置です。①の額縁検出すら、「55pxのものを見つけて拡大する」という目的のために存在しています。**このパイプラインは、大きさの違いを潰すための仕掛けである**、と要約できます。

## 7. 主張 ── 次に何をすべきで、何をすべきでないか

### 主張1: より新しい検索モデルへの差し替えは、今やるべきではありません

この分野の2025〜2026年の主要な進展は、より強い大域記述子（DINOv3、SSCD）とより強い局所照合器（EDM、RoMa v2）です。しかしそれらが解決するのは「**正解が候補の上位に入ってこない**」という問題です。

**実験Cで確認した通り、この39枚では正解が候補から漏れた例は0件です。** 検索段の上限は 39/39 です。上限に達していないのは出力段です。上限を引き上げる投資は、上限に当たっていない状況では1点も精度を生みません。

**やるべきは、`438100_50` と `438100_61` の2枚目落ちを追うこと**です。原因の候補は3つあり、いずれも既存のパラメータで検証できます:
- `--max-props 4`（候補領域の上限）が足りていない
- `--iou-thresh 0.30`（重複除去）が、隣接する2枚を重複と誤判定している
- `--budget 32`（検証回数）を1枚目が使い切っている

これは**手法の差し替えではなく、既存パラメータの切り分け**です。差し替えより先にこれをやるのが順序として正しい。

### 主張2: precision 1.000 を「実力」と読んではいけません

この数字が出た条件を正確に述べます。**参照データベース327枚に対し、クエリ39枚が実際に写しているのは10枚（era1の全て）だけです。残り317枚は一度も正解にならない、単なる邪魔者です。**

この構成では、「era1のポスターを、era1以外の317枚と取り違えなかった」ことしか分かりません。**測れていないのは、era内での取り違えです。** 例えば era5 には『ゴッドファーザー』『タクシードライバー』『ブレードランナー』が並び、era4 には113枚が集中しています。同じ作品の別バージョンポスターや、同じシリーズのポスターが近接している領域は、**構造的に混同しやすいのに、今回のクエリはそこに1枚も当たっていません。**

**したがって、era2〜era7 のスクリーンショットとラベルを作ることが、今できる測定の中で最も価値が高い作業です。** これをやらずに「92.3%」を報告するのは、測っていない部分を測ったかのように見せることになります。

### 主張3: このパイプラインの設計は「前処理で問題を簡単にする」であり、それは正しい

一連の測定を並べると、一貫した構造が見えます。

- 学習ベースの照合器（LightGlue、19ms）を捨てて、1980年代の RANSAC と2004年の比率検定（0.5ms）を使い、**精度は上がった**（34/39 → 36/39）
- 深層学習の特徴抽出器を1999年の SIFT に替えても、**精度は下がらなかった**
- 一方で、**古典的な前処理（額縁検出・切り出し拡大・CLAHE・5解像度DB）を外すと精度は明確に落ちる**（前任者の記録: 拡大先を1024→800に下げるだけで3件失う）

**つまりこの問題の難しさは、「照合が難しい」ことではなく「照合するものの条件を揃えるのが難しい」ことにあります。** 55pxのポスターと3926pxの参照画像を、暗い部屋越しに、斜めから比べる ── これを「同じくらいの大きさの、同じくらいの明るさの、正面に近い画像同士」に変換してしまえば、あとは古典手法で十分です。

**新しいモデルは、条件を揃えられない状況を力技で押し切るために存在します。条件を揃えられる状況では、揃えた方が安くて速くて正確です。**そしてVR内のポスターは平面で、参照画像と同一のビットマップに由来し、深度も法線も取れる ── **条件を揃えるための情報が、実写の画像検索より圧倒的に多く手に入る状況です。** ここに投資するのが筋だと考えます。

## 8. この報告が主張していないこと（限界）

読み間違いを避けるため、明示します。

1. **era1 以外は評価していません。** §7 主張2 の通り。327枚中10枚しか当たっていない評価です。
2. **39枚は統計的に小さいです。** 完全正解率の95%信頼区間は [79.7%, 97.3%] と幅広く、SuperPoint と SIFT の差は測れていません。

4. **126 ms は GB10（デスクトップ級GPU）での値です。** スタンドアロンVRヘッドセット上の性能は全く未知です。§5.5 の通り、その環境では抽出器の選択自体を見直す必要があります。
5. **ガイドエージェント部分（LLM）は一切扱っていません。** 今回の対象は「どのポスターか」を当てるところまでです。
6. **SIFT 比較で前任者の Windows 測定と逆の結果が出た件は、原因を特定していません。**
7. **SuperPoint の学習済み重みは Magic Leap の非商用ライセンスです。** 研究用途では問題ありませんが、商用化する場合はここが障害になります（ALIKED や DISK は Apache-2.0 なので差し替え可能）。
