# 映画解説データはPostgresに一元化し、来場者からのリクエストは1つの共有サーバーで捌く

## この文書は何のためにあるか

これは「なぜこの設計にしたか」を後から読む人（自分自身も含む）が思い出せるようにする記録（ADR = Architecture Decision Record）です。コードを読むだけでは分からない「当時の判断理由」を残すのが目的です。

## 前提：このプロジェクトは何をしようとしているか

VRChat（VR空間で複数人が集まれるプラットフォーム）上に「映画史博物館」というワールドを作っている。壁には映画ポスターが時代順に貼られていて、来場者はそこを歩き回れる。ここに「今見ているポスターについて喋ってくれるAIガイド」を置きたい。

そのために必要な処理の流れは次の3段階：

1. **画像認識**：来場者の画面（VRChatのスクリーンショット）に写っているポスターが、どの参照ポスター画像と一致するかをコンピュータビジョンで当てる。この部分は既に実装・検証済み（`match_fast.py`など）。
2. **データ取得**（今回この文書が扱う部分）：画像認識が「このポスターだ」と特定したら、その映画についての解説文などのデータをデータベースから取ってくる。
3. **AI応答**：取ってきたデータをもとに、LLM（ChatGPTのような大規模言語モデル）が来場者と自然な会話をする。この部分はまだ作っていない。

今回のADRは、上記の2番目「データ取得」と、それを支えるインフラをどう作るかについての決定です。

## 決めたこと、とその理由

### (1) データベースは Postgres を使い、映画テーブルと章テーブルの2つだけを持つ

```
chapters（時代/章のテーブル）: 章の番号、タイトル、年代範囲
movies（映画のテーブル）: 映画タイトル、原題、公開年、所属する章、そして長い解説文
```

「解説文を書く作業」自体は、これまで通り読みやすい Markdown ファイル（`film-impression-museum-exhibition-plan.md`）で行い続け、取り込みスクリプトでPostgresへ流し込む。**「人間が書く場所」と「プログラムが検索しにいく場所」を分けた**、というのがこの決定の実質。

### (2) 画像認識が返す「id」は、Postgresの映画テーブルの主キー（movie_id）そのものとする

1つの映画のポスターを複数の角度・距離から撮った参照写真が何枚もあるが、それらは「同じ1枚のポスターの写真違い」であって別のポスターではない（1つの映画にはポスターが基本的に1枚しかないという事実を確認済み）。

だから「どの写真がどの映画のものか」を解決する処理は画像認識システムの中だけで完結させ、画像認識が最終的に外へ返す値は最初から「映画のID」にする、と決めた。この結果、データ取得側で必要なSQLは次の1つだけになる：

```sql
SELECT m.title_zh, m.title_orig, m.year, m.essay_md, c.title_zh AS chapter_title
FROM movies m JOIN chapters c ON c.id = m.chapter_id
WHERE m.id = $1;
```

もし画像認識の出力を「特定の1枚の参照写真」のままにしていたら、Postgres側に「写真→映画」の対応表をもう1つ持ち、上のSQLにJOINをもう1段追加する必要があった。**そのJOINを1段減らすために、写真と映画の対応付けという仕事を画像認識システム側に寄せた**、というのがこの決定の中身。

### (3) システムは1つの共有サーバーが全来場者からのリクエストを受け、データベースもそのサーバー1つが持つ

VRChatワールドは複数人が同時に訪れる場所であり、来場者Aが見ているポスターと来場者Bが見ているポスターは別々に、かつ同時に問い合わせが発生しうる。この「同時に複数の問い合わせが来る」状況を、来場者ごとに独立したプログラム（各自のPC上で動くローカル完結のプロセス）で処理するか、1つのサーバーに集約して処理するかを選ぶ必要があった。

選んだのは後者。理由は次の具体的な事情による：**このシステムで内容が変わりうるのは「映画の解説文」であり、これは`film-impression-museum-exhibition-plan.md`を編集するたびに更新される。** サーバーを1つにしてデータベースもそこに1つだけ置けば、解説文を直したときにサーバー上のPostgresを更新するだけで、その場にいる全来場者に即座に新しい内容が反映される。逆に各来場者のPCごとにデータベースファイルを持たせる方式（後述のSQLite案）だと、解説文を1箇所直すたびに、そのファイルを全来場者のPCにコピーし直す配布作業が別途必要になる。

つまりここで交換したのは、**「来場者PC1台で完結する実装の単純さ・ネットワーク不要という気軽さ」を手放す代わりに、「解説文の更新をサーバー側の1箇所で行うだけで全員に反映できる一元管理のしやすさ」を取った**、というトレードオフである。

## 検討したが採用しなかった案

- **各来場者のPC上で完結させる案**（データベースもローカルの軽量なファイル（SQLite）に置き、AIガイドのプログラムも各自のPCで動かす）：
  作るのは簡単だが、上記(3)で書いた通り、解説文を1箇所直すたびに全員のPCへファイルを配り直す作業が発生する。この配布コストが、来場者が増えるほど・解説文の修正回数が増えるほど積み重なると判断し、採用しなかった。

- **画像認識が返すIDを「特定の1枚の参照写真」のままにしておき、データベース側に「どの写真がどの映画のものか」を対応付ける専用テーブルを別に作る案**：
  上記(2)で書いた通り、「1つの映画にはポスターは基本的に1枚しかない」という事実が確認できたため、この対応付けテーブルを持つこと自体に得られる情報がなく（同じ映画を指す複数の写真を区別して保持する理由がない）、テーブルとJOINを1つ増やすだけの効果しかないため、採用しなかった。
